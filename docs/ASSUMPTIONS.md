# Assumptions register

Team 7, Jurong Marine. Written 15 Nov 2026 from the code on branch `enhance/rag-hardening`.

This register is adapted from the reference project's register (`reference/rag_capstone/docs/ASSUMPTIONS.md`). Only the assumptions that apply to this repo are kept. Each one has a basis, what happens if it is wrong, where it lives in this repo, and how the app shows it to the user. The rule is the same as in the reference: when an answer depends on an assumption, the app says so in a note added by code, not only in the model's wording.

Left out from the reference: A11 (embeddings and vision; this repo uses neither), A12 (folded into A3), A13 and A16 (readings made by a vision model; this repo reads images with Tesseract, see A18).

## Assumptions

| ID | Topic | Assumption | Basis | If wrong | Where it lives | How the app shows it |
|---|---|---|---|---|---|---|
| A1 | Severity scale | Incidents dated before 1 Jul 2025 use a scale where 1 is worst; from that date 5 is worst. For a single-scale view, old values are converted as `6 - logged`. Only the exact pairing (old 1 = new 5, and so on) is assumed. | The GM brief email in the SOP folder states the change. The scanned forms print their scale on the form, and the incident OCR import reads that label before falling back to the date. | Change the conversion in `jm_rag/sources_mysql.py` and `jm_rag/facts.py` (`_normalised_severity`). | `severity_scale` and `severity_5_worst` set in `jm_rag/sources_mysql.py`; `SEVERITY_FLIP` in `jm_rag/notes.py`; `resolve_scale` in `scripts/ingest_incident_reports.py` | Severity questions whose evidence spans the change get the note "Incident severity changed scale on 1 Jul 2025 ...". Computed facts say the mapping "is not confirmed in the CMMS", and code makes that caveat a required part of a worst-case or severity-level answer. |
| A2 | Spares "ALL" | The spares row listed for machine `ALL` is never expanded to individual machines. | The nameplates read more than one lubricant grade, so one oil cannot fit every machine. | Nothing to undo; this is the safe default. | `_lubricant_vs_all` and `_spares_all_unresolved` in `jm_rag/conflicts.py` | Lubricant answers show a conflict note ending "`ALL` is left unresolved and is not expanded to machines". A machine's spares answer marks the `ALL` row "Unresolved". |
| A3 | Personal data | Employee names are never shown. Injury data is given as aggregate counts only. Per-person rankings and incident details about one person are refused. Technician codes on work orders are allowed. The OCR reviewer's name is personal data and never reaches evidence or answers. | The strictest privacy choice. It is easy to loosen later and impossible to un-leak. | Add roles and a restricted view. | `jm_rag/guardrails/` (input guard classes NAME_REQUEST, PERSON_RANKING, PERSON_INCIDENTS, PRIVATE_DATA; output guard; `sanitize.PERSONAL_KEYS`) | A refusal message that offers counts by year, machine, shift or severity instead. If a name slips into a draft, the output guard replaces the whole answer. |
| A4 | Shift hours | Day shift is 07:00 to 18:59 Singapore time and night shift is 19:00 to 06:59. Sensor timestamps are stored in UTC and shifted by 8 hours. | The CMMS does not record shift times. | Change the `CASE WHEN HOUR(...)` expression in `jm_rag/sources_mysql.py`. | `jm_rag/sources_mysql.py` (shift SQL); `SHIFT_NOTE` in `jm_rag/sensors.py` | The shift source text says "Shift hours are assumed: day 07:00-18:59 and night 19:00-06:59 Singapore time; the CMMS does not record shift times." Without that source in the evidence, a shift question abstains with a note. |
| A5 | Spares currency | Spares costs are in SGD. Work-order costs are in SGD (the column is `cost_sgd`). | The workbook states no currency; the company is in Singapore. | Change the wording in `jm_rag/facts.py`. | `spares_facts` in `jm_rag/facts.py`; `jm_rag/key_figures.py` | Computed facts say "the workbook states no currency; SGD is assumed, not confirmed". For a cost question, code makes this caveat required. |
| A6 | Conflicting sources | When sources disagree, the order of trust is SOP, then nameplate, then CMMS free text. For incidents, the CMMS `safety_incidents` record outranks the OCR of the form. A human-approved OCR value outranks raw OCR. Both sides are always shown. | SOPs are the controlled documents. The CMMS incident table is the system of record; form OCR is unverified. | Change the conflict wording in `jm_rag/conflicts.py` and `jm_rag/conflicts_records.py`. | Module docstring and conflict texts in `jm_rag/conflicts.py` and `jm_rag/conflicts_records.py`. The system prompt has no trust order; it tells the model to cite both sides and not to choose silently. | The conflict note names the side it trusts and why, for example "The SOP is the controlled document and is trusted; both are shown." The outcome badge is Conflict. |
| A7 | Coverage and end date | Only CNC-01, CNC-02, CNC-03, CMP-01 and PMP-T01 have sensor data. No data exists after 30 Jun 2026. | The package holds nothing else. The sensor list is not hard-coded; it is read from the loaded sensor sources. | Nothing to change in code; new data is picked up when loaded. | `DATA_END` in `jm_rag/config.py`; `sensor_tags` in `jm_rag/tags.py`; the sensor checks in `plan_query` (`jm_rag/retrieval.py`) | A sensor question about another machine abstains with "I have no sensor data for ... Sensor readings exist only for ...". Later dates and forecasts abstain with "The data ends on 30 Jun 2026, so I cannot answer for later dates or forecast them." Every computed-facts source ends with the data-end date. |
| A8 | Sensor data quality | The sensor `machine_id` is the CMMS asset tag. Readings logged in Fahrenheit are converted to Celsius at load; the original value and unit are kept. ISO timestamps without a timezone are rejected, not guessed. Whether the vendor smoothed the CNC-02 trend cannot be checked. | Same ID text in both sources. The loader records the conversions. | Fix the loader and reload. | `scripts/sensor_csv_to_mysql.py` (`parse_timestamp`, temperature conversion); `jm_rag/sensors.py` | Sensor trend sources say they are descriptive statistics, not a fault diagnosis or threshold alert. A Fahrenheit question gets code-converted values with "stored in Celsius". |
| A9 | Possible duplicate person | Employee codes that share a full name are flagged as possible duplicates, not merged. | A shared name does not prove one person. | None. | `identity_gap` in `jm_rag/gaps.py`; the codes-only `employee_data_quality` source in `jm_rag/sources_mysql.py` | "I cannot confirm whether ... are the same person ... names are withheld." The outcome is Cannot answer fully. |
| A10 | "Test pump sump" | The phrase in an SOP is not mapped to PMP-T01. | Mapping it would be a guess. | Add an alias for PMP-T01. | No code maps it; machine aliases come from the machines table only. | SOP answers quote the SOP text as written. |
| A11 | Model access | The app uses an OpenAI-compatible chat endpoint (default model `gpt-4o-mini`, temperature 0, 30-second timeout, one SDK retry). An empty `OPENAI_BASE_URL` means the OpenAI default URL. | Measured: the e2e eval runs in Phase 5 reached the API. | Every model path falls back to a code-built answer from the evidence. | `LazyClient` in `app.py`; `jm_rag/drafting.py` | Without a key: "The AI endpoint is not configured, so this lists the retrieved evidence directly." Endpoint down: "The AI endpoint is unavailable, ...". |
| A14 | Relative dates | Relative periods are read against the end of the data, not today's date. "This year" (also "year to date") means 2026, "last year" means 2025, "this month" means June 2026 and "last month" means May 2026. "Recently" and "latest" mean newest records first; they are not mapped to a date window. | The data ends on 30 Jun 2026 and the demo runs after that. | Change `resolve_relative_periods` in `jm_rag/dates.py`. | `resolve_relative_periods` in `jm_rag/dates.py`, called by `jm_rag/pipeline.py` before retrieval | The computed facts name the date range they cover (for example `2025-01-01 to 2025-12-31`), and the model is told to state it. No separate note announces the mapping. |
| A15 | Maintenance schedule | The data holds no forward schedule or service intervals. An open work order is something already raised, not a planned date. | `work_orders` holds past and open items only. | If the client supplies a PM plan, add a source and a tool. | `asks_schedule` flag (`jm_rag/guardrails/patterns.py`); `SCHEDULE_NOTE` in `jm_rag/notes.py` | "When is the next service due?" abstains with "The data holds past and open work orders only, so I cannot give the next service or due date." |
| A17 | Retrieval | Keyword retrieval with TF-IDF is good enough for this corpus. Machine tags in the question restrict the candidates before ranking. No embeddings, no reranker. | The corpus is small and the questions name machines, SOP topics and record types. The retrieval eval passes tier 1 at 29/29. | Paraphrased questions with no shared words can miss evidence. Add an embedding search behind the same `retrieve` function. | `retrieve` and `plan_query` in `jm_rag/retrieval.py` (scikit-learn `TfidfVectorizer`, word 1- and 2-grams, English stop words, fitted per question on the filtered candidates) | The evidence panel shows what was retrieved. A question with an unknown machine tag says "I could not find a machine with the ID ...". |
| A18 | OCR readings | Nameplate and incident-form images are read with Tesseract (pytesseract, with OpenCV preprocessing). Every OCR value is unverified until a person approves it. | Measured on 15 Nov 2026 against the team's checked reference readings (12 nameplates, 30 forms): 66 of 113 structured nameplate fields match (58%); 17 of 24 raw-text readings next to a label match (71%); 121 of 150 incident-form fields match (81%). Employee codes and descriptions are not compared. | Wrong OCR values reach answers as unverified readings. Fix them in the OCR Review tab. | `scripts/nameplate_ocr_import.py`, `scripts/ingest_incident_reports.py`; `python -m scripts.ocr_accuracy_report` (counts only) | OCR evidence is labelled "UNVERIFIED OCR" and answers carry "Some values come from OCR that is not human-verified; those are labelled unverified and may be wrong." Eval cases that fail because of OCR are labelled "OCR data error, fix via OCR Review". |
| A19 | OCR review tables | A reviewed value is trusted only when its decision is APPROVED. Raw OCR rows are never changed; corrections are stored separately and applied on read. | The review gate already existed and keeps raw evidence intact. | Rejected and pending records are both shown as unverified; there is no separate "rejected" label. | `ocr_review_decisions` (status, corrections JSON, notes, reviewer); `effective_record` in `scripts/ocr_review.py`; `nameplate_assets_staging` and `incident_report_ocr` staging tables | Approved values are labelled "HUMAN-VERIFIED" in the evidence. The reviewer field is removed from evidence and answers. |
| A20 | Name screening list | The output guard screens the names in the `employees` table, plus any names in the optional `data/guard/extra_terms.txt`. People who are not employees are screened only if they are added to that file. | The list is built from MySQL, read-only, by `python -m scripts.build_guard_terms`; it prints counts only. | A non-employee's name in a document could reach an answer. | `jm_rag/guardrails/names.py`; `scripts/build_guard_terms.py`; `data/guard/name_terms.json` (git-ignored) | If the list is missing, the sidebar warns that names cannot be screened and every request trace carries `names_unloaded`. |
| A21 | Prices for cost monitoring | Token prices come from `OPENAI_INPUT_COST_PER_1M_USD` and `OPENAI_OUTPUT_COST_PER_1M_USD`. With neither set, `gpt-4o-mini` on the default URL is priced at USD 0.15 and 0.60 per 1M tokens; any other setup is unpriced. | The prices are set in `.env`. | Costs shown are wrong by the price error; token counts stay right. | `api_cost_rates` in `jm_rag/observability.py` | An unpriced call is shown and stored as unknown, never as $0. |
